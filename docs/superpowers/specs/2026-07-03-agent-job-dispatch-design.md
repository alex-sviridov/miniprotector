# Agent & Event-Driven Job Dispatch — Design

> This is proposal #1 of two architectures under discussion for remote job orchestration: a
> queue-consumer / event-driven `agent`. A second proposal (rules-driven with reconciliation) is
> being brainstormed next; this doc may be superseded or merged with it once that comparison is
> done.

## Problem

Today, running a backup means someone (or cron) invokes `brfs` directly on the source host.
There's no way for the control plane to *trigger* a backup remotely — and per the existing
`Control Plane vs. Agents` network model (`docs/ARCHITECTURE.md`), agents only ever dial out, so a
push-based RPC from control plane to agent isn't an option without breaking that invariant.
Separately, cert renewal today is a bare cron entry calling `certclient`, with no orchestration or
observability.

## Goals

- Control plane can enqueue a "run `brfs`" job for a specific host; that host picks it up and
  executes it without any inbound connection to the agent.
- One new node-level binary (`agent`) per node, replacing the ad hoc cron entry for cert renewal
  and adding job dispatch — but staying thin: it schedules and executes, it doesn't reimplement
  `certclient`'s or `brfs`'s logic (shells out via `exec.Command`).
- The agent's code surface does not grow as more capabilities are orchestrated through it — adding
  a new dispatchable action is a config change, not a code change.
- Survives agent restarts and crashes mid-job without losing or silently double-running jobs,
  leveraging the existing `--job-id`-based idempotency already built into
  `backup_jobs`/`file_versions` (see `docs/superpowers/specs/2026-07-02-backup-job-tracking-design.md`).

## Non-Goals (v1)

- No scheduler component — jobs are published by hand via the `nats` CLI against a documented
  subject/payload convention. A future scheduler can publish through the same convention later.
- No per-host authorization in NATS — all agents share one NATS identity; `jobs.<hostname>` is a
  routing convention, not a server-enforced security boundary. The queue must only be reachable by
  trusted operators/network segments for v1. Revisit real per-host authz (static per-host NATS
  accounts regenerated by `certrequest`, or a NATS auth-callout service) once this queue gets a
  producer surface beyond a trusted operator.
- No config-push action type. The allowlist mechanism (below) makes this a small future addition,
  not a redesign, but it isn't built now.
- No dead-letter consumer/alerting surface — messages that exhaust `MaxDeliver` simply stop being
  redelivered; nothing reads or surfaces the dead-letter subject yet.

## Architecture

Two new pieces:

1. **NATS (JetStream)** — new control-plane component, deployed alongside `ca`/`catalog` in
   `deploy/control-plane/`. Provides a durable, per-host stream (`jobs.<hostname>`) so a job
   published while an agent is offline is still delivered once it reconnects. JetStream uses a
   file-backed store for durability across NATS restarts.

2. **`agent`** — new per-node binary, replacing the current cron-driven `certclient` invocation.
   It is a **trigger layer over one generic executor** — there is no per-capability Go code:

   ```go
   func Execute(action string, args []string) error {
       binary, ok := allowlist[action]
       if !ok {
           return ErrUnknownAction
       }
       cmd := exec.Command(binary, args...)
       return cmd.Run()
   }
   ```

   Two independent trigger sources feed this one executor:
   - **Cert-renewal ticker**: `time.Ticker` at `CertRenewalIntervalSec`, calls
     `Execute("certclient", nil)`. Does not depend on NATS connectivity — keeps running even if
     the queue is unreachable.
   - **Job queue consumer**: a durable JetStream pull-consumer on `jobs.<hostname>`, calls
     `Execute(msg.Action, msg.Args)` per received message.

   `allowlist` is config-driven (`action → binary path`), not hardcoded. Adding a new
   remotely-triggerable capability (e.g. a future `rwfs verify` trigger) means adding one allowlist
   entry, not writing new agent code — consistent with the project's existing pattern of one
   single-purpose binary per capability (`brfs`, `rwfs`, `certclient`): if a new capability needs
   in-process logic that can't be expressed as "run an existing binary," it should be built as its
   own new binary and added to the allowlist, not folded into `agent`.

## Data Flow

```
Operator (nats CLI)
  → publish to jobs.<hostname> (JetStream stream, durable)
       payload: {"job_id": "<uuid>", "action": "brfs", "args": ["--destination", "...", "/path"]}

agent (on <hostname>)
  ticker loop:
    every CertRenewalIntervalSec → Execute("certclient", nil)   // no NATS involved

  queue loop:
    durable pull-consumer on jobs.<hostname>
      → receive message
      → decode JobMessage; unknown JSON shape → Term (no redelivery), log error
      → action, ok := allowlist[msg.Action]; !ok → Term (no redelivery), log error
      → if action == "brfs" and msg.JobID != "": inject `--job-id <job_id>` into args
      → err := Execute(action, args)
      → err == nil: Ack (removes message from stream)
      → err != nil: Nak with backoff (JetStream redelivers after AckWait, up to MaxDeliver)
```

**Why `job_id` rides in the message rather than being generated by `brfs` itself**: if the agent
crashes after `brfs` completes but before it acks the NATS message, JetStream redelivers the same
message on reconnect. Reusing the same `job_id` on redelivery makes the re-run a no-op through the
already-idempotent `EnsureBackupJob`/`EnsureFileVersion` upsert path (first-write-wins on
`(job_id)` / `(job_id, object_id)`) — no new dedup logic needed in the agent; it falls out of the
existing backup-job-tracking design for free.

## Message Schema

```go
type JobMessage struct {
    JobID  string   `json:"job_id"`  // reused verbatim as brfs's --job-id; empty means brfs generates its own
    Action string   `json:"action"`  // key into the agent's allowlist config
    Args   []string `json:"args"`    // passed through to exec.Command verbatim, no shell interpretation
}
```

`Args` are passed as an argv array to `exec.Command`, never through a shell — no shell-injection
surface regardless of message content. The open risk given deferred authz (see Non-Goals) is that
any producer able to publish to the queue can run any allowlisted binary with arbitrary flags; the
allowlist bounds *which programs* can run, not *which arguments* they're given. Acceptable for v1
because the queue's producer side is a trusted operator, not an open surface.

## Config (new `local.conf` keys, following the existing `catalog_host`/`ca_host` pattern)

- `nats_host` / `nats_port` — JetStream server the agent connects to
- `agent_allowlist` — `action → binary path` map (e.g. `brfs=/usr/local/bin/brfs`,
  `certclient=/usr/local/bin/certclient`)
- `CertRenewalIntervalSec` — ticker cadence for the cert-renewal trigger
- `JobConsumerAckWaitSec` — JetStream redelivery timeout for a job that never acked
- `JobMaxDeliverAttempts` — cap on redelivery attempts before JetStream stops retrying a message
  *(default: 5)*
- `AgentNatsMaxBackoffSec` — cap for reconnect backoff when NATS is unreachable at startup or
  drops mid-run

## Deployment

New `nats` service in `deploy/control-plane/docker-compose.yml` alongside `ca`/`catalog`,
JetStream enabled with a file-backed volume for durability. `agent` connects to NATS over mTLS
using its existing `certclient`-issued identity — the same certs dir every other component
(`bwfs`, `brfs`, `rwfs`, `catalogsync`) already reads via `common/mtls`.

## Error Handling

- **NATS unreachable at agent startup or mid-run**: reconnect with exponential backoff (same
  shape as `catalogsync`'s: start at 1s, cap at `AgentNatsMaxBackoffSec`). The cert-renewal ticker
  loop is independent and keeps running regardless of NATS state.
- **Durable consumer doesn't exist yet on a fresh NATS deployment**: agent idempotently
  creates it on startup (create-if-absent), rather than requiring an operator to pre-provision it
  — mirrors the `EnsureBackupJob` idempotent-create pattern used elsewhere.
- **Unknown `action` in a message, or malformed JSON**: terminated without redelivery (poison
  message — retrying can't fix a config/schema problem) and logged at error level. Distinct from
  exit-code failures below, which *are* redelivered since they may be transient.
- **`Execute` returns non-zero exit or an error** (including "binary in allowlist but missing on
  disk"): message is Nak'd, JetStream redelivers after `JobConsumerAckWaitSec`, up to
  `JobMaxDeliverAttempts` before the message stops being redelivered (no dead-letter consumer
  reads it yet — Non-Goal).
- **Agent crash mid-`brfs`-execution**: the message was never acked, so JetStream redelivers once
  the agent restarts and reconnects. Because `job_id` is reused from the message payload, the
  redelivered run's `EnsureBackupJob`/`EnsureFileVersion` calls are idempotent no-ops for anything
  already durably written. Known limitation: if the original `brfs` child process survives the
  agent's crash (e.g., reparented to init) while the agent restarts and redelivery re-executes it,
  two `brfs` processes could run concurrently against the same `job_id` for a window — not a
  correctness bug (the write path is idempotent per the job-tracking design), but a resource-usage
  inefficiency. Killing the child's process group on agent shutdown is a nice-to-have, not
  required for v1.
- **Agent restart with the cert-renewal ticker mid-run**: no persistence needed — a restart just
  means the next tick retries; `certclient` is documented as safe to invoke redundantly ("Always
  renews when invoked").

## Testing

- Unit: allowlist lookup rejects an unknown action without invoking `exec`.
- Unit: `JobMessage` JSON (de)serialization round-trip, including the empty-`JobID` case.
- Unit: `Execute` distinguishes success / non-zero exit / binary-not-found.
- Integration (extends the `src/e2e/` harness): publish a job to a live NATS/JetStream instance,
  run `agent`, assert `brfs` actually executed (e.g. a file appears via `bwfs list`) and the
  message was acked (no redelivery on a second poll).
- Integration: kill the agent mid-job (before ack), restart it, assert redelivery occurs and the
  reused `job_id` results in exactly one `backup_jobs` row and one `file_versions` row per file —
  not duplicates.
- Integration: cert-renewal ticker invokes `certclient` on schedule (using a short interval in
  test).
