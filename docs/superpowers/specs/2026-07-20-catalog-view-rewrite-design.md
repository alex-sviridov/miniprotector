# Design: Catalog View Rewrite

**Date:** 2026-07-20
**Status:** Approved for planning

## Problem

`CatalogView.vue` has several real, user-reported defects:

1. **Filters don't work.** The view layers two independent, differently-scoped filter/pagination
   systems on one table: a custom form (Source Host / Store Host / Pattern + Search) that hits the
   server and refetches, and `simple-datatables` mounted with no options, which adds its own
   default search box (`searchable: true`) and 10-row client-side pagination on top. Typing into
   the DataTable's own search box only searches whatever ~100 rows are currently loaded from the
   server — not the whole catalog — so a user searching for something on a different server page
   sees "no results" and reasonably concludes filtering is broken. This is a direct regression from
   the pattern the Jobs page established one day earlier
   ([Design: Jobs pages for `web`](2026-07-19-jobs-frontend-design.md)), which deliberately kept
   only one search mechanism.
2. **Prev/Next is misaligned with `simple-datatables`.** The custom cursor-based Prev/Next sits
   below a table that also has DataTable's own default pagination controls rendered inside it —
   two visually similar pagers with different scopes and different page sizes.
3. **Versions cannot be opened.** `simple-datatables` reads the initial table into its own internal
   data model once at construction (`readTableData`) and owns all subsequent row rendering via its
   own diffDOM-based virtual DOM — confirmed by its own delegated `mousedown` listener
   (`datatable.ts:636`) and per-feature `emit()` calls, none of which know about Vue. Vue's
   `@click="openVersions(group)"` binding exists only on the DOM Vue renders at mount; once
   DataTable takes over (immediately), any row it subsequently (re)renders during a sort/search/page
   action loses that binding entirely. Jobs/Clients never hit this because their rows are plain
   text with no per-row interactivity — Catalog is the first page to need one.
4. **Source host is an opaque ID, not a hostname**, in the demo. Traced to
   `demo/docker-compose.yml`'s `database`/`webserver` services having no `hostname:` field, so
   Docker assigns each container's autogenerated container ID as its OS hostname, which `brfs`
   reports verbatim via `os.Hostname()`. The deeper root cause — `brfs` never adopting the
   cert-derived identity `agent`/`certclient` already use, and `catalog` trusting a self-reported
   value instead of `bwfs`'s already mTLS-validated peer hostname — is out of scope for this
   design; see **See Also** for the separate follow-up.
5. **Size isn't human-readable** — raw byte counts are rendered directly; no `formatBytes`-style
   utility exists anywhere in `web/src`.
6. **Version grouping can undercount across a page boundary.** Grouping only ever covered whatever
   page of raw entries was currently loaded (an accepted limitation in the prior design), so a
   file's versions split across a Prev/Next boundary were undercounted.
7. Minor: a raw `"null"` string renders for any zero/absent timestamp (missing the `|| '—'`
   fallback used elsewhere, e.g. `JobsListView.vue`), and (structural) the 164-line view mixes
   fetch/filter orchestration, grouping, DataTable lifecycle, and a hand-built modal in one file,
   unlike the rest of `web`'s single-purpose components.

## Scope

**In scope:**
- `web/src/stores/catalog.js` — replace cursor-based pagination with a fetch-all-matching-pages
  loop per search
- `web/src/views/CatalogView.vue` — restructured filter/search/DataTable wiring
- `web/src/components/VersionsModal.vue` — new, extracted from the inline modal
- `web/src/utils/format.js` — add `formatBytes`
- `demo/docker-compose.yml` — add `hostname:` to the `database` and `webserver` services so the
  demo's `source_host` values are readable, as a stopgap ahead of the real fix (see **See Also**)

**Out of scope:**
- Any change to `api-server`'s `/catalog` response shape, or to `catalog.proto`
- Making `brfs`/`bwfs`/`catalog` derive `source_host` from the mTLS peer certificate instead of
  self-reported `os.Hostname()` metadata — a separate, immediately-following design (see **See
  Also**)
- Live-tail/polling of catalog data — still fetch-on-search, no auto-refresh
- Changes to `JobsListView.vue` or `ClientsListView.vue`

## Architecture

The custom filter form (Source Host / Store Host / Pattern) is the *only* search mechanism.
`simple-datatables` is configured with `searchable: false` so it never shows a competing search
box — it is used purely to render, sort, and paginate whatever the form's Search has already
fetched.

Because grouping must see every entry matching the current filter to avoid ever splitting a
file's versions across a page boundary, the custom cursor-based Prev/Next UI is removed entirely.
On Search, `catalog.js` loops the existing keyset-paginated `/catalog` endpoint internally
(requesting the maximum `limit=500` each call) until the server reports `has_more: false`,
accumulating every matching entry before handing them to `groupEntriesByFile`. `simple-datatables`'s
own pagination (`perPage: 25`) becomes the only pager in the UI, operating over the complete,
correctly-grouped result set — this also eliminates the dual-pagination-UI confusion, since only
one pager remains.

Because catalog size has no natural bound (unlike Jobs' 24h window), the view never fetches on
mount. The Search button is disabled until at least one of the three filter fields is filled, so an
unbounded whole-catalog fetch is never possible.

Row interactivity (opening the versions modal) cannot be wired via a template `@click`, since
DataTable owns row DOM after mount. Instead, `simple-datatables` emits `datatable.selectrow` on
every row click via its own listener attached once to the table element for its lifetime
(`datatable.ts:636`), reporting a `rowIndex` that stays a stable index into whatever data array
was fed to it at construction — unaffected by the library's own internal sort/page state. The view
registers one handler for this event after constructing DataTable, mapping `rowIndex` back into
`groups.value`.

## Components

### `web/src/stores/catalog.js`

Cursor-pagination state and actions (`cursorStack`, `hasMore`, `canGoPrev`, `nextPage`, `prevPage`)
are removed entirely. `search(filters)` becomes:

```js
async search(filters) {
  this.filters = { ...filters }
  this.loading = true
  this.error = null
  const collected = []
  try {
    let startingAfter
    for (;;) {
      const qs = buildQuery(this.filters, startingAfter, 500)
      const body = await apiFetch(`/catalog?${qs}`)
      collected.push(...body.data)
      if (!body.has_more || body.data.length === 0) break
      startingAfter = body.data[body.data.length - 1].id
    }
    this.entries = collected
  } catch (err) {
    this.error = err.message
    this.entries = []
  } finally {
    this.loading = false
  }
}
```

`buildQuery` gains a third `limit` parameter, always passed as `500` (the server's documented
max) to minimize the number of round trips. A failure partway through the loop discards everything
collected so far (`entries = []`) rather than displaying a partial, possibly-mis-grouped result —
consistent with the store's existing single-`try`/`catch` convention.

### `web/src/views/CatalogView.vue`

- The Search button is disabled via `computed(() => !form.sourceHost && !form.storeHost &&
  !form.pattern)`. No all-empty search can reach the store.
- No fetch on mount. A local `hasSearched` ref distinguishes the pre-search empty state ("Enter a
  filter and search") from a post-search zero-result state ("No entries match this filter").
- `renderTable()`: groups `catalog.entries` via the unchanged `groupEntriesByFile`, destroys any
  existing DataTable, and constructs `new DataTable(tableRef.value, { searchable: false, perPage:
  25 })`. Immediately after, it registers:
  ```js
  dataTable.on('datatable.selectrow', (rowIndex) => {
    const group = groups.value[rowIndex]
    if (group && group.versions.length > 1) selectedGroup.value = group
  })
  ```
- The Versions column renders plain text (the count, or nothing for a single-version file) — no
  button, no per-row Vue event binding.
- The inline modal markup is replaced with `<VersionsModal v-if="selectedGroup" :group="selectedGroup"
  @close="selectedGroup = null" />`.
- The Prev/Next buttons and their template block are removed.

### `web/src/components/VersionsModal.vue` (new)

Extracted from the current inline modal, unchanged in behavior: props `{ group }`, emits `close`.
Owns its own `keydown` (Escape-to-close) listener (added/removed in its own `onMounted`/
`onBeforeUnmount`), backdrop-click-to-close, and Close button. Every timestamp renders through
`formatTimestamp(...) || '—'`; every size renders through `formatBytes(...)`.

### `web/src/utils/format.js`

Add:

```js
const UNITS = ['B', 'KB', 'MB', 'GB', 'TB']

export function formatBytes(bytes) {
  if (bytes === null || bytes === undefined) return '—'
  if (bytes === 0) return '0 B'
  let exponent = Math.min(Math.floor(Math.log(bytes) / Math.log(1024)), UNITS.length - 1)
  let value = bytes / 1024 ** exponent
  if (exponent > 0 && Number(value.toFixed(1)) >= 1024 && exponent < UNITS.length - 1) {
    exponent += 1
    value = bytes / 1024 ** exponent
  }
  return `${exponent === 0 ? value : value.toFixed(1)} ${UNITS[exponent]}`
}
```

Binary units (1024-based), matching filesystem-size conventions. `null`/`undefined` render as
`'—'` (matching `formatTimestamp`'s existing fallback convention); `0` renders as `'0 B'` — a
legitimate empty file is distinguished from an absent/undecodable value.

### `web/src/utils/catalogGrouping.js`

Unchanged. The function was already correct; it simply now always runs over the complete filtered
result set instead of one server page.

### `demo/docker-compose.yml`

Add `hostname: database` to the `database` service and `hostname: webserver` to the `webserver`
service, so `os.Hostname()` inside those containers — and therefore the demo's `source_host`
values — read as the intended names instead of Docker's autogenerated container ID. This is an
explicit stopgap: the real fix (making `source_host` derive from the already mTLS-validated peer
identity `bwfs` computes, rather than a self-reported OS hostname) is a separate, immediately-
following design (see **See Also**) that will make this correct in any deployment, not just the
demo.

## Data Flow

Mount → nothing fetched, pre-search empty-state message shown. User fills in at least one filter
field (Search enables) → submit → `catalog.search()` loops `/catalog` in 500-row batches until
`has_more` is false → `catalog.entries` holds the complete matching set → `renderTable()` groups
everything and (re)builds `DataTable` → all further interaction (column sort, page, click a row to
open its versions) is client-side against that complete set until the next Search.

## Error Handling

- An all-empty filter search is prevented client-side (disabled Search button) — the store never
  receives one.
- A failure partway through the multi-page fetch loop discards everything collected so far
  (`entries = []`) and surfaces `error`, rather than rendering a partial, possibly-mis-grouped
  table.
- Per-entry `Metadata` decode failures are unchanged — `toProtoEntry` already degrades those fields
  to zero values; no new handling is introduced here.
- The versions modal only opens for `group.versions.length > 1`; a single-version row's click is
  inert, matching today's behavior of showing no button/affordance for those rows.

## Testing

- **`stores/catalog.spec.js`** (rewritten): `search` loops until `has_more: false`, concatenating
  every page's `data` into `entries`; every request includes `limit=500`; a failure on any page
  clears `entries` and sets `error`. All `cursorStack`/`nextPage`/`prevPage` tests are deleted.
- **`utils/format.spec.js`**: new `formatBytes` cases — `0`, sub-1024 values, exact unit
  boundaries (1024, 1024*1024, ...), large multi-unit values, `null`/`undefined` → `'—'`.
- **`views/CatalogView.spec.js`**: Search button is disabled when all three fields are empty and
  enabled when any one is filled; no fetch occurs on mount; `DataTable` is constructed with
  `{ searchable: false, perPage: 25 }`; invoking the mocked DataTable's registered
  `datatable.selectrow` callback with a multi-version row's index opens `VersionsModal` with the
  right group, and with a single-version row's index does nothing. Prev/Next tests are removed.
- **`components/VersionsModal.spec.js`** (new): today's `CatalogView.spec.js` modal-behavior
  assertions (renders versions newest-first, closes via Close button / backdrop click / Escape)
  move here, unchanged in substance, now exercised against the standalone component.
